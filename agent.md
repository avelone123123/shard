## 2. ЖЕЛЕЗНЫЙ ЗАКОН: КАТЕГОРИЧЕСКИЙ ЗАПРЕТ НА ХАРДКОД
- В проекте Shard запрещен любой хардкод, моки, симулированные ответы и фейковые заглушки.
- Каждая строчка кода обязана быть функциональной, реальной и исполняемой.
- Запрещено подделывать вывод токенов, имитировать работу оборудования или возвращать статичные захардкоженные структуры.
- Все вызовы должны проходить через реальный C++20 FFI, реальные векторные регистры MASM AVX2 или живой стриминг Hugging Face Hub API.
- Любой агент, допустивший хардкод, признается скомпрометированным, а его изменения немедленно откатываются через Git.
## 3. ИНЖЕНЕРНЫЙ ФОКУС: C++20, x86_64 MASM AVX2, PYTHON
- HTML (dashboard.html) — это лишь вспомогательный интерфейс для мониторинга ядра и визуализации метрик.
- Агентам запрещено бесконечно переписывать верстку. Основной инженерный ресурс (90%) должен направляться на ядро:
- 1. native/shard_core.cpp: прямое проецирование весов моделей в виртуальную память через Win32 MapViewOfFile/VirtualAlloc, пулы тензорных буферов, SIMD деквантование Q4_K/Q8_0/FP16, zero-copy FFI.
- 2. native/shard_asm.asm: ручная векторизация на чистом ассемблере x86_64 MASM с использованием инструкций AVX2, FMA3 (vfmadd231ps, vmovups, ymm0-ymm7), достижение максимального GFLOPS на ватт.
- 3. engine.py и server.py: реальный асинхронный инференс, распределение слоев нейросети между VRAM видеокарты и системной RAM, стриминг токенов через SSE без накладных расходов.
## 4. ДИСТРИБУЦИЯ И ПРОСТОТА УСТАНОВКИ В ОДИН КЛИК
- Конечный пользователь должен разворачивать проект одной командой в консоли, аналогично ведущим открытым пакетам:
- Установка через pip: pip install shard-engine или pip install -e .
- Автоматическая компиляция нативных библиотек shard_core.dll через native/build_native.py во время сборки пакета.
- Доступность глобальной консольной команды: shard start, shard run <model>, shard status, shard test, shard key.
- Никаких сложных ручных настроек или плясок с бубном: одна команда в терминале запускает сервер и нативный рантайм.
## 5. ПОСТОЯННОЕ ХРАНИЛИЩЕ ВЕСОВ МОДЕЛЕЙ И DOCKER
- Веса нейросетей, скачанные с Hugging Face, и артефакты агентов не должны теряться или уходить в никуда.
- Проект обязан поддерживать четкую структуру постоянного дискового хранилища: ~/.cache/shard/models и /data/models.
- Для полной изоляции и серверов развернуто Docker-окружение (Dockerfile и docker-compose.yml) с именованными томами:
- Volume shard_models_volume: монтируется в /data/models, защищая веса моделей от удаления при пересоздании контейнера.
- Volume shard_data_volume: сохраняет ключи доступа keys_db.json и историю диалогов.
- Запуск через docker compose up -d поднимает изолированный инференс-сервер со всеми зависимостями на порту 8000.
